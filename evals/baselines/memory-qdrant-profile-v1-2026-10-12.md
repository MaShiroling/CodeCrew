## 瓶颈结果

占比是 profiled **独占样本耗时之和/根耗时之和**，不是 p95 比。
每个样本独占阶段的和严格等于根时长；inclusive 嵌套阶段和各阶段 p95 不可相加。

| 合成档 | 前/后规范快照合计占比 | 快照 SELECT 次数（前+后） | 元数据 HTTP 占比 | 查询 HTTP 占比 |
| --- | --- | --- | --- | --- |
| 10 / 10 | 25.54% | 32+32=64 | 30.42% | 14.66% |
| 50 / 50 | 46.06% | 152+152=304 | 15.89% | 18.34% |
| 200 / 200 | 59.39% | 602+602=1204 | 8.08% | 19.50% |
| 200 / 1000 | 57.84% | 602+602=1204 | 7.80% | 20.00% |

200/200 档根均值 88.170 ms，前快照 p50=24.789、后快照 p50=24.985 ms；这两个
p50 只展示阶段分布，不能当成同一次调用的总快照 p50。规范快照 SELECT 数是
`2 × (3N+2)`，包含每候选 revision/规范缓存/根来源查询及每次两条元数据查询。
**1204 是两次快照的 SELECT，不是完整 retrieve 的全部 SQL**；初始候选、BM25、
最终复验另外统计。trace 不计连接打开的 PRAGMA，FTS 内部注释语句归 OTHER。

所有实际非空 Qdrant 召回均观测到 **5 次 collection GET + 1 次 points/query POST**。
两次 `_require_sync_ready` 各两次 GET，搜索适配器还有一次 readiness GET。
缓存质量小候选时，元数据 HTTP 占 38.10%、查询 HTTP 占 17.20%，前后规范快照
仅占 6.91%。说明瓶颈随候选数变化，不是单一“Qdrant 引擎慢”。

HTTP 含 JSON 编解码、网络与服务处理，本轮不采服务端 `time`，不是裸引擎计时。
规范快照包含数据库查询，也含来源解析、BLOB/哈希、有限性/float32/维度和契约
构造等 Python 工作；本轮**没有**把 SQL 执行与 Python CPU 分开。因此只证实
逐条读取形状及快照阶段占比，不能说 59.39% 全是 N+1 SQL，也不能承诺改批量
SQL 后能消除这些耗时。缓存查询向量不是云模型，生产云成本/延迟另计。
